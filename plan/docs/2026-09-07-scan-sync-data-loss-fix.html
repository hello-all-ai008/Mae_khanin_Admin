ข้อมูลสแกน Checkpoint หายเพราะเครื่องสแกนเขียนทับกัน

เคสตั้งต้น: BIB 1860 — ยิง CP ไปแล้วแต่ข้อมูลหาย เพราะเครื่องสแกนคนละเครื่อง sync ทับกัน ไม่ใช่เพราะลบ Station CP

🔴 CRITICAL — ข้อมูลจริงหายได้ทุกเมื่อ ⏱ วันแข่ง 12-13 ก.ย. — เหลือ 5 วัน 🗄 ต้องแก้ที่ Database (Supabase Live) 📄 สถานะ: รอ Gong อนุมัติก่อนลงมือ
⚠️ สรุปสั้น ๆ เครื่องสแกน CP แต่ละเครื่องเก็บข้อมูลนักวิ่งไว้ในเครื่องตัวเอง (cache) แล้วเวลาส่งข้อมูลขึ้น Supabase มันส่ง ทั้งก้อน cps ที่มีอยู่ในเครื่อง ไปทับของเดิมบน server เลย — ไม่ได้ merge ทีละจุด ถ้าเครื่องไหน cache เก่า (ยังไม่รู้ว่ามีคนสแกนจุดอื่นไปแล้ว) พอมันยิงสแกนของตัวเอง มันจะเขียนทับจุดอื่นที่เคยสแกนไปแล้วให้หายหมด
  • BIB 1860 โดนทับ 3 รอบติดจนเหลือ cps: {} ว่างเปล่า — ทั้งที่ยิงจริงไปแล้ว 3 จุด (Start, A1, A2)
  • เจอ CP ในบันทึก log แต่ข้อมูลหายไปแล้วอีก 3 คน: BIB 5114, 5115, 5134
  • บั๊กเดียวกันนี้เกิดกับ Check-in และ Finish ได้เหมือนกัน (เขียนทับเวลาแทนที่จะยึดเวลาแรก)

2สาเหตุที่แท้จริง

ไม่เกี่ยวกับการลบ Station CP — ตรวจสอบแล้วว่าการลบ station ในหน้าตั้งค่า ไม่มีโค้ดส่วนไหนไปแตะข้อมูลนักวิ่งเลย และเวลาที่ลบก็ไม่ตรงกับช่วงที่ข้อมูลหาย

เครื่องสแกน CP → อ่าน cps จาก cache ในเครื่อง (ไม่ได้เช็คกับ server สด ๆ) → เพิ่มจุดที่เพิ่งยิงเข้าไปในก้อน → ส่งก้อนทั้งหมดทับ server
ทำไมถึงอันตรายวันแข่งจริง วันแข่งมีหลายจุด (Start / A1 / A2 / Finish) แต่ละจุดมีเครื่องสแกนของตัวเอง — นักวิ่งคนเดียวถูกสแกนจากหลายเครื่องเป็นเรื่องปกติ ไม่ใช่เคสพิเศษ ถ้าเครื่องไหนไม่ได้เปิดหน้าเว็บใหม่ (เพื่อดึงข้อมูลล่าสุด) ก่อนยิง มันจะเขียนทับจุดอื่นให้หายทันที — เกิดขึ้นได้กับนักวิ่งทุกคน ทุกจุด ตลอดการแข่ง

เจอปัญหาข้างเคียงอีก 2 จุดระหว่างตรวจโค้ด:

จุดปัญหาผลกระทบ
เวลาเข้าเส้นชัย (Finish) เขียนทับเวลาตรง ๆ ไม่เช็คว่ามีอยู่แล้วหรือยัง เครื่อง cache เก่ายิง Finish ซ้ำ อาจทับเวลาที่ถูกต้องด้วยเวลาที่ช้ากว่า
การส่งข้อมูลขึ้น server ไม่เช็คผลลัพธ์ว่าจริง ๆ เขียนเข้า database สำเร็จไหม ถ้าเขียนไม่ผ่าน (ระบบสิทธิ์บล็อก) แอปคิดว่าสำเร็จ ทิ้งคิวทันที ข้อมูลหายเงียบ ๆ ไม่มี error ให้เห็น
คิวส่งข้อมูล (Sync Queue) ถ้ารายการหัวคิวส่งไม่ผ่าน จะลองใหม่ทุก 2.5 วิ ไม่มีวันหยุด รายการที่ค้างจะบล็อกทุกสแกนที่ต่อคิวข้างหลังทั้งหมด — ทั้งจุดหยุดทำงานได้

3แผนการแก้ไข

✅ ก่อนแก้ (ตอนนี้)

// เครื่องส่งก้อนทั้งหมดทับ update runners set cps = {ก้อนที่เครื่องมี} where id = ...

ไม่มีการเช็คว่า server มีข้อมูลอะไรอยู่ก่อน — ใครส่งทีหลังชนะเสมอ ต่อให้ข้อมูลเก่ากว่า

🔧 หลังแก้

// server รวมทีละจุด ไม่ทับก้อนทั้งหมด update runners set cps = cps || {จุดที่เพิ่งยิง} where id = ... and ยังไม่เคยมีจุดนี้

ทำงานฝั่ง database (Postgres Function) โดยตรง — เครื่องไหนส่งมาก็ตาม จุดเดิมจะไม่มีวันถูกลบทิ้ง

3.1 สร้างฟังก์ชันกลางบน Database (RPC เดียวคุมทั้ง 3 แบบสแกน)

ฟังก์ชันเดียวชื่อ record_scan ใช้ทั้ง Check-in / CP / Finish — หลักการ "จุดแรกที่ยิงชนะเสมอ" ตัดสินที่ server ไม่ใช่ที่เครื่อง:

ประเภทวิธีเขียนข้อมูลใหม่
CPเติมเฉพาะจุดที่ยังไม่เคยมี — จุดที่เคยยิงแล้วจะไม่ถูกแตะเลย
Finishเขียนเฉพาะตอนที่ยังไม่มีเวลาเข้าเส้นชัย — มีแล้วจะไม่ถูกทับ
Check-inเขียนเฉพาะตอนที่ยังไม่เคยเช็คอิน — เช็คอินแล้วจะไม่ถูกเปลี่ยนเวลา

ระบบสิทธิ์ (RLS) ที่มีอยู่แล้วในระบบเป็นคนคุมสิทธิ์การเขียนให้อัตโนมัติ (เจ้าหน้าที่ที่ล็อกอินถูกต้องเท่านั้นที่เขียนได้) — ไม่ต้องเปิดช่องโหว่เพิ่ม และถ้าเขียนไม่ผ่านจริง ๆ (เช่นสิทธิ์ไม่พอ) แอปจะเห็น error ทันที ไม่ทิ้งคิวแบบเงียบ ๆ เหมือนตอนนี้

3.2 กู้คืนข้อมูลที่หายไปแล้ว

ระบบมีตาราง "บันทึกการสแกนทุกครั้ง" (scan_logs) เก็บหลักฐานไว้แยกต่างหาก ยังไม่หาย — ใช้กู้คืนเฉพาะจุดที่ขาดหายจาก cps ปัจจุบันได้ โดยไม่แตะข้อมูลที่ยังอยู่ครบ:

BIBสถานะปัจจุบันพบใน Logหลังกู้คืน
1860cps ว่างเปล่าStart, A1, A2กู้คืนครบ 3 จุด
5114cps ว่างเปล่าA1กู้คืน 1 จุด
5115cps ว่างเปล่าA1กู้คืน 1 จุด
5134cps ว่างเปล่าA1กู้คืน 1 จุด
หมายเหตุ อีก 26 คนที่มีข้อมูล cps อยู่แล้วจะไม่ถูกแตะเลย ต่อให้เวลาในบันทึกกับเวลาในข้อมูลจริงต่างกันไม่กี่วินาที (ความต่างของนาฬิกาเครื่อง vs server) — ของเดิมที่มีอยู่ถือเป็นค่าที่ถูกต้องเสมอ กู้คืนเฉพาะที่ "หายไปทั้งหมด" เท่านั้น

3.3 ซ่อมคิวส่งข้อมูล ไม่ให้ค้างบล็อกกันทั้งจุด

  • รายการที่ส่งไม่ผ่านซ้ำ ๆ จะถูกเลื่อนไปท้ายคิวแทนที่จะค้างขวางหัวคิวตลอดไป
  • เพิ่มการรอนานขึ้นเรื่อย ๆ ระหว่างลองใหม่ (ไม่ยิงรัวทุก 2.5 วิเหมือนเดิม)
  • ถ้าลองซ้ำจนครบจำนวนแล้วยังไม่ผ่าน จะพักไว้ในถังแยกต่างหาก พร้อมแจ้งเตือนบนหน้าจอ — เห็นชัดว่ามีรายการค้าง ไม่หายไปเงียบ ๆ

3.4 เครื่องสแกนแก้ cache ตัวเองอัตโนมัติ

ทุกครั้งที่สแกนสำเร็จ เครื่องจะรับค่าจริงจาก server กลับมาอัปเดต cache ตัวเองทันที (ไม่ต้องเพิ่มระบบ realtime ใหม่ตามที่คุยกันไว้) — ลดโอกาสที่เครื่อง cache เก่าจะไปทับข้อมูลคนอื่นในสแกนครั้งถัดไป

4ขั้นตอนตรวจสอบก่อนใช้งานจริง

  • 1 ทดสอบ: จำลอง 2 เครื่อง cache คนละเวอร์ชัน ยิงคนละจุด → ต้องเห็นข้อมูลอยู่ครบทั้ง 2 จุด (จำลองบั๊กเดิมซ้ำ ต้องไม่เกิดอีก)
  • 2 ตรวจ BIB 1860 / 5114 / 5115 / 5134 → cps ต้องกลับมาครบตาม log
  • 3 ตรวจ BIB ที่มีข้อมูลอยู่แล้ว (เช่น 1126, 1501, 1710) → ต้องไม่เปลี่ยนค่าที่มีอยู่
  • 4 ทดสอบยิงซ้ำ (rescan) จุดเดิม → ต้องไม่เปลี่ยนเวลาที่บันทึกไว้ครั้งแรก
  • 5 ทดสอบคิวค้าง (จำลองส่งไม่ผ่าน) → ต้องไม่บล็อกสแกนอื่นที่ตามมา และมีแจ้งเตือนให้เห็น
  • 6 ทดสอบจริงบนหน้าสแกน 2 เครื่องพร้อมกัน ก่อนส่งให้ verifier ตรวจอีกรอบ

5สิ่งที่ไม่ได้แก้ในรอบนี้

ยังคงค้างจากรอบก่อน — ควรกลับมาดูก่อนวันพิมพ์ BIB หน้าสร้างบัตร BIB (GenerateBibModal) ยังมีบั๊กดึงข้อมูลได้สูงสุด 1000 แถวเหมือนเดิม (งานนี้มี 1064+ คน) — Gong เลือกเลื่อนแก้ไปก่อนหน้านี้ ยังไม่ได้แตะในแผนนี้
เอกสารนี้เป็นแผนก่อนลงมือแก้ — ยังไม่มีการเปลี่ยนแปลงใด ๆ บนระบบจริง
