1. สรุปผลงานที่ดำเนินการเสร็จสิ้นในวันนี้ (13 ก.ย. 2026)

1.1 ปรับแต่งระบบพิมพ์สลิปอิเล็กทรอนิกส์ (Thermal E-Slip Calibration)

  • แก้ไขปัญหาพื้นหลังโลโก้ดำด่างในหน้า Preview และตอนพิมพ์จริง:

    เดิมทีโลโก้บ้านโป่ง (Baan Pong) และแม่ขะนิง (Mae Khaning) มีการใช้ CSS mix-blend-mode: multiply ซึ่งเมื่อส่งคำสั่งพิมพ์ไปยังไดรเวอร์เครื่องพิมพ์ความร้อน (Thermal Receipt Printer) โหมดสี Monochrome จะแปลงพิกเซลโปร่งแสงให้กลายเป็นบล็อกสีดำเข้ม ได้ทำการลบ Multiply Blend ออก และใช้ฟิลเตอร์ filter: grayscale(100%) พร้อมบังคับพื้นหลังขาวสะอาด ทำให้รูปพิมพ์คมชัดสวยงาม

  • ตัดข้อมูลส่วนเกินของเบราว์เซอร์ออกทั้งหมด (Zero Browser Header/Footer):

    ยกเลิก Header ด้านบนซ้าย (วันที่และเวลา), ด้านบนขวา (URL rohn-runner) และลิงก์ด้านล่างสุด โดยใช้คำสั่ง @page { margin: 0 !important; } และปรับ CSS ให้สลิปสะอาดเหมือนใบเสร็จจริง พร้อมนำ URL สลิปทางการ rohn-runner.vercel.app/eslip/[bib] ฝังลงในกรอบล่างสุดของตัวสลิป

  • ปรับให้ขนาดสลิปพอดีกับเนื้อหาบนกระดาษม้วนต่อเนื่อง 80mm:

    ยกเลิกการล็อกความสูงแบบคงที่ (เช่น 140mm หรือ 210mm) ที่ทำให้เกิดพื้นที่ว่างด้านล่างมากเกินไป เปลี่ยนเป็น Natural Content Flow (height: auto !important; max-height: none !important;) สลิปจะยาวพอดีกับเนื้อหาการวิ่ง ไม่เหลือช่องว่าง และไม่ตัดขึ้นแผ่นที่สอง

  • แก้ปัญหาสลิปชิดขอบกระดาษด้านขวา:

    ปรับสมดุล Padding เป็น 1.5mm 3mm 1.5mm 2mm !important ภายในความกว้างสลิป 70mm บนพื้นที่พิมพ์ 72.1mm ทำให้ระยะขอบซ้ายและขวาอยู่กึ่งกลางพอดี ไม่เบียดขอบขวา

  • ขยายขนาดตัวหนังสือและโลโก้ให้ชัดเจนอ่านง่าย:

    ปรับความสูงโลโก้หัวกระดาษเป็น 75px, โลโก้แม่ขะนิงเป็น 46px, โลโก้ ROHN เป็น 60px พร้อมปรับขนาดตัวหนังสือในตารางเวลาและ Checkpoint ให้อ่านง่ายบนกระดาษความร้อน

  • เปลี่ยนข้อความหัวสลิป:

    เปลี่ยนข้อความใต้โลโก้บ้านโป่งจากคำว่า Official e-Slip เป็นตัวเลขปี 2026 ตามที่ผู้ใช้งานกำหนด

  • แสดงยอดจำนวนคนรวมใน Overall Rank และ Age Group (Rank / Total):

    อัปเดตช่องแสดงผลอันดับเป็น <อันดับ> / <จำนวนคนทั้งหมด> เช่น 1 / 767 ในอันดับรวม (Overall Rank) และ 1 / 85 ในรุ่นอายุ (Age Group) โดยคำนวณจากจำนวนผู้เข้าร่วมทั้งหมดในระยะนั้น (allInDist และ allInCat) กรอง BIB ทดสอบของระบบออก และตั้งค่า white-space: nowrap !important; ป้องกันข้อความตัดขึ้นบรรทัดใหม่

1.2 พัฒนาหน้ารายงานสรุปผลการแข่งขัน (SummaryReport.jsx ใน Rohn-Runner)

2. รายละเอียดปัญหาและจุดที่ติดขัดในปัจจุบัน (Current Technical Friction)

⚠️ สรุปประเด็นสำคัญ: โครงสร้างฐานข้อมูลที่ใช้งานอยู่ในปัจจุบัน (Production Legacy) ยังเป็นแบบตารางเดี่ยว (Flat Table) และเก็บเวลาสแกนใน JSONB cps ซึ่งยังไม่สอดคล้องกับสถาปัตยกรรมเชิงสัมพันธ์แบบหลายงานวิ่ง (Multi-Event Relational Schema) ที่ถูกออกแบบไว้ในหน้า DatabaseFlow.jsx

1. การจัดเก็บเวลาใน JSONB (runners.cps)

ปัญหา: ข้อมูลจุดสแกนถูกบันทึกในรูปแบบ Key-Value ในคอลัมน์ runners.cps (เช่น {"checkin": ..., "st_1": ..., "finish": ...}) ซึ่งมีรูปแบบ Key ไม่สม่ำเสมอในบางเรคคอร์ด ทำให้โค้ดฝั่งหน้าบ้านต้องเขียน Logic ตรวจสอบ Key สลับไปมาหลายชั้น แทนที่จะสามารถคิวรีจากตารางจุดตรวจได้โดยตรง

2. การคำนวณอันดับและจำนวนคนรวมใน Client Memory

ปัญหา: การคำนวณอันดับและยอดรวม 1 / 767 ในปัจจุบัน ต้องดึง Array ของนักวิ่งทั้งหมดในระยะนั้นมาวนลูปและเรียงลำดับ (Sort) ใน RAM ของเบราว์เซอร์ หากมีนักวิ่งจำนวนหลักพันถึงหลักหมื่นคน จะส่งผลต่อประสิทธิภาพการโหลด และหากมี BIB ระบบ (เช่น RUNNER_CONFIG หรือ __...) ปะปนมาจะทำให้ตัวหารผิดเพี้ยนหากไม่กรองทิ้ง

3. ความหน่วงระหว่าง public_results และ runners

ปัญหา: แอปพลิเคชันฝั่งนักวิ่ง (Rohn-Runner) อ่านข้อมูลจาก public_results ในขณะที่แอดมิน (Rohn-Admin) เขียนข้อมูลลงตาราง runners โดยตรง หากระบบ RPC Sync หรือ Rebuild ผลลัพธ์มีความล่าช้า นักวิ่งอาจเห็นผลการแข่งขันหรือสลิปไม่อัปเดตในทันที

4. ข้อมูลระยะทางและรุ่นอายุเป็นข้อความอิสระ (Raw Strings)

ปัญหา: ฟิลด์ cat และ age_group ถูกเก็บเป็น String (เช่น "MKT10", "10 KM : Hard Rock", "ชาย 30-39") ขาด Foreign Key เชื่อมไปยังตาราง CATEGORIES ทำให้การจำแนกสีระยะทางและรุ่นอายุต้องพึ่งพา Regex Parser

3. แหล่งข้อมูลที่ควรจะใช้ อิงตามโครงสร้างใน DatabaseFlow.jsx

เพื่อให้ระบบมีความเสถียร รองรับงานวิ่งขนาดใหญ่และหลายงานวิ่งพร้อมกัน (Multi-Event) ข้อมูลแต่ละส่วนควรถูกอ้างอิงจากตารางหลักตามที่ระบุไว้ใน DatabaseFlow.jsx ดังนี้:

หมวดหมู่ข้อมูล แหล่งข้อมูลปัจจุบัน (Legacy) แหล่งข้อมูลที่ถูกต้องตาม DatabaseFlow โครงสร้างตารางและฟิลด์สำคัญ ประโยชน์ที่จะได้รับเมื่อปรับใช้
ข้อมูลงานวิ่ง (Event) Hardcode หรือระบุใน RaceContext ตัวเดียว EVENTS id (PK UUID), name, start_date, end_date, status รองรับการจัดงานวิ่งหลายๆ งานในระบบเดียวกันโดยข้อมูลไม่ปะปนกัน
โปรไฟล์นักวิ่ง (User Master) ซ้ำซ้อนในตาราง runners ทุกงาน USERS id (PK UUID), name, email, phone, gender, birth_date นักวิ่งใช้โปรไฟล์เดียวสมัครได้ทุกงาน วันเกิดคำนวณรุ่นอายุอัตโนมัติถูกต้องแม่นยำ
ข้อมูลการสมัครและบิบ (Registration) ตารางเดี่ยว runners ปะปนข้อมูลส่วนตัวและผลการแข่งขัน RUNNERS id (PK), event_id (FK), user_id (FK), category_id (FK), bib, rfid_tag, registration_status แยกข้อมูลการสมัครออกจากโปรไฟล์หลัก ป้องกันเลข BIB ชนกัน และผูก Foreign Key ชัดเจน
ระยะการแข่งขันและสี (Categories) String ตัดคำใน cat และ cat_name CATEGORIES id (PK), event_id (FK), name, distance_km, unit, color สีกราฟ สีแท็ก และระยะทางถูกควบคุมจากจุดเดียว ไม่ต้องเขียน Regex แปลงข้อมูล
จุดตรวจและ Cutoff Time (Checkpoints) Array ฝังใน Config หรืออ่านจาก JSON STATIONS & CHECKPOINT category_id (FK), station_id (FK), sequence_order, cutoff_time กำหนดเส้นทางและเวลา Cutoff แยกตามแต่ละระยะวิ่งได้อย่างยืดหยุ่น
ประวัติการสแกนเวลา (Scan Records) JSONB runners.cps SCAN_LOGS id (PK), runner_id (FK), station_id (FK), scan_time, is_valid, scanned_by เก็บประวัติการสแกนทุกครั้งอย่างโปร่งใส ตรวจสอบย้อนหลังได้ว่าใครเป็นผู้สแกนและเวลาใด
รายชื่อเจ้าหน้าที่ผู้สแกน (Staff Directory) State ชั่วคราวในหน้าจอแอดมิน STAFF id (PK), event_id (FK), name, role, status บันทึกชื่อ Marshal หรือเจ้าหน้าที่ที่จุดตรวจลงในสลิปและประวัติการสแกนได้ถูกต้อง

4. แผนงานและข้อแนะนำสำหรับก้าวถัดไป (Next Steps)

  1. สร้าง Database View / RPC คำนวณอันดับจากฐานข้อมูลโดยตรง:

    สร้างฟังก์ชัน get_runner_ranks(runner_bib, event_id) ใน PostgreSQL โดยใช้คำสั่ง DENSE_RANK() OVER (...) และ COUNT(*) OVER (...) เพื่อให้ได้ทั้งอันดับและจำนวนคนรวมแบบเรียลไทม์ โดยไม่ต้องดึง Array นักวิ่งทั้งหมดมาคำนวณบนเบราว์เซอร์

  2. เชื่อมโยง category_id ในตาราง runners:

    ทำการ Backfill ฟิลด์ category_id ในตาราง runners ให้ชี้ไปยังตาราง categories เพื่อให้การจัดกลุ่มและการคำนวณยอดคนในแต่ละระยะทางแม่นยำ 100%

  3. บันทึก Scan Event ลงใน scan_logs ควบคู่กับ cps:

    เมื่อเจ้าหน้าที่สแกนเวลาที่จุดตรวจ ให้ระบบส่งข้อมูลลงตาราง scan_logs พร้อมบันทึก scanned_by เพื่อเป็น Audit Trail และอัปเดต runners.cps สำหรับการอ่านผลลัพธ์แบบแคชที่รวดเร็ว
