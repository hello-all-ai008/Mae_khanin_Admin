1.2 ปรับปรุงการเพิ่มนักวิ่ง Manual ด้วยข้อมูลจริงจาก Database (ImportRunners.jsx)

เปลี่ยนจากช่องกรอกข้อความเปล่า (Free-text) มาเป็นแบบ ดึงตัวเลือกจาก Database ของ Event ที่เลือกมาแสดง 100%:

  • ระยะทาง/หมวดหมู่: รวมข้อมูลจากตาราง categories และที่เคยมีใน runners ขึ้นมาให้คลิกเลือกได้ทันที
  • กลุ่มอายุ (Age Group): ดึงรุ่นอายุที่มีใน Database มาเรียงลำดับตามตัวเลขอัตโนมัติ พร้อมตัวเลือก กำหนดเอง...
  • สัญชาติ (Nationality): มีสัญชาติเริ่มต้นและดึงจาก DB พร้อมตัวเลือกกรอกเอง
  • เพศ (Gender): บังคับมาตรฐานภาษาอังกฤษเท่านั้น (Male / Female) ตัดปัญหา M, F หรือภาษาไทย เพื่อความสม่ำเสมอของฐานข้อมูล
  • ปุ่มแนะนำ BIB ถัดไป (Auto): วิเคราะห์หาหมายเลข BIB ตัวเลขที่สูงที่สุดใน DB แล้วบวกหนึ่งให้อัตโนมัติ
  • ระบบแจ้งเตือน BIB ซ้ำแบบ Real-time: แจ้งเตือนทันทีหากหมายเลข BIB ชนกับนักวิ่งคนอื่นในระบบ

1.4 จัดรูปแบบคอลัมน์ cat, cat_name, distance, unit ให้ตรงมาตรฐาน

แก้ไขปัญหาที่ก่อนหน้านี้คอลัมน์ cat_name ถูกบันทึกเป็น null ให้ตรงตามมาตรฐานเดียวกับการนำเข้าไฟล์ Excel:

  • หน้า Import นักวิ่งแบบ Manual
  • Modal แก้ไขข้อมูลนักวิ่ง (EditRunnerModal)
  • Dropdown ตัวเลือกแสดง 5 KM : Soft Rock

1.5 ปุ่มสลับโหมด Auto / ออฟไลน์ บนสถานีสแกน (NetworkModeToggle.jsx)

เพิ่มฟังก์ชันให้เจ้าหน้าที่ควบคุมโหมดการเชื่อมต่อได้เอง ติดตั้งไว้ข้างๆ ปุ่มตั้งค่า ใน 3 หน้าหลัก (CheckIn, CheckPoint, FinishLine):

  • โหมด Auto (เขียว): ทำงานปกติ มีเน็ตส่งข้อมูลขึ้น Supabase อัตโนมัติ เน็ตหลุดจะพักไว้ในคิวรอส่ง
  • โหมด ออฟไลน์ (แดง): บังคับตัดการเชื่อมต่อเครือข่าย หยุดการส่งข้อมูลออก ข้อมูลการสแกนทั้งหมดจะถูกเซฟลงเครื่องและคิวอย่างปลอดภัย 100%
  • คลิกเดียวสลับโหมด: เมื่อกลับมาเป็น Auto ข้อมูลที่ค้างอยู่จะถูกทยอยส่งขึ้นคลาวด์ให้อัตโนมัติทันที

2 สิ่งที่ต้องติดตามและข้อควรระวัง (Watch Items & Pending Fixes)

⚠️ 1. ข้อมูลนักวิ่งเก่าใน Supabase (Legacy Rows)

แถวข้อมูลนักวิ่งที่ถูกเพิ่มเข้ามาก่อนหน้านี้บางรายการในตาราง runners มี cat_name เป็น null หรือมี cat ที่ไม่มีคำนำหน้าระยะกิโล (เช่น มีแค่ Soft Rock):

  • ข้อแนะนำ: รันสคริปต์ SQL Update ใน Supabase SQL Editor หรือใช้เมนู Admin Data Rebuild เพื่อตัดคำและอัปเดต cat_name ให้เป็นปัจจุบันสำหรับแถวเก่าเหล่านั้น

ℹ️ 2. การอ้างอิงชื่อตาราง Checkpoint ในไฟล์ Migration เก่า

ในไฟล์ migration ประวัติศาสตร์เดิมบางไฟล์มีการเขียนชื่อตารางเป็นพหูพจน์ checkpoints แต่ตารางจริงในระบบตาม DatabaseFlow.jsx คือ checkpoint (เอกพจน์):

  • แนวทาง: ให้ใช้ชื่อ checkpoint ตามที่ระบุในสถาปัตยกรรมหลักเสมอ

3 การอ้างอิงแหล่งข้อมูลในระบบ (อิงตาม DatabaseFlow.jsx)

ตามโครงสร้าง Multi-Event ใน DatabaseFlow.jsx แหล่งข้อมูลสำหรับแต่ละส่วนงานต้องอ้างอิงดังนี้:

ข้อมูล / ความต้องการ ตารางหลัก (Primary Table) คอลัมน์ที่ใช้งาน คำอธิบายและการนำไปใช้
การคัดกรองงานวิ่ง events id, name, status ใช้เป็นตัวกรองหลัก (Scope) ของทั้งระบบ หากเปลี่ยนงาน ข้อมูลนักวิ่งและจุดสแกนจะโหลดใหม่ตาม event_id
หมวดหมู่ / ระยะทาง (ชื่อสะอาด) runners / categories runners.cat_name, categories.name ชื่อประเภทการแข่งขันที่ไม่มีตัวเลขกิโลปน (เช่น Soft Rock, Hard Rock)
ระยะทางรวมชื่อรุ่น (แบบสมบูรณ์) runners runners.cat สตริงรวมสำหรับแสดงผลหน้าเว็บและ Leaderboard รูปแบบ [ระยะ] KM : [ชื่อรุ่น]
ตัวเลขระยะทาง & หน่วย runners / categories distance (float), unit (varchar) ตัวเลขระยะทาง (เช่น 5, 10) และหน่วย 'KM'
สีประจำรุ่น categories color รหัสสี Hex (เช่น #FF5733) สำหรับการ์ดหน้า Monitor และ Badge
หมายเลข BIB runners bib รหัสประจำตัวนักวิ่ง ต้องไม่ซ้ำกันในงานเดียวกัน (UNIQUE ต่อ event_id)
เพศ runners gender เก็บเป็นภาษาอังกฤษตัวเต็ม: 'Male' หรือ 'Female'
กลุ่มอายุ runners age_group (สำรอง: age) รุ่นอายุการแข่งขัน เช่น 20-29, 30-39 หรือ Overall
จุดสแกนและเวลา Cutoff stations & checkpoint stations.type, checkpoint.cutoff_time กำหนดว่าจุดสแกนเป็น START, CP หรือ FINISH และเวลา Cutoff ของแต่ละรุ่น
ประวัติการสแกนเวลา scan_logs runner_id, station_id, scan_time, scanned_by บันทึกเวลาที่สแกนผ่าน RPC ลง Database เป็นข้อมูลอ้างอิงจริง
